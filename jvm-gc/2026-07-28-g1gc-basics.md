# G1GC Cơ bản (Garbage-First Garbage Collector)

- **Date:** 2026-07-28
- **Topic:** jvm-gc
- **Level target:** Middle+ / Senior

## 1) Câu hỏi phỏng vấn

**G1GC hoạt động như thế nào? Khác gì so với CMS/Parallel GC? Khi nào nên dùng G1GC?**

---

## 2) Giải thích đơn giản (cho người không background)

**G1GC (Garbage-First)** là bộ dọn rác của JVM, thay thế CMS từ Java 9.

Hãy tưởng tượng heap là một **kho hàng lớn**. Thay vì quét toàn bộ kho mỗi lần (như Parallel GC) hoặc chỉ dọn khu vực cũ (như CMS), G1GC:

| Khái niệm | Giải thích đời thường |
|-----------|----------------------|
| **Region** | Chia kho thành nhiều **ngăn nhỏ bằng nhau** (1-32MB), mỗi ngăn chứa object young hoặc old |
| **Young GC** | Dọn các ngăn chứa object mới (age = 0) — nhanh, thường xuyên |
| **Mixed GC** | Dọn young + một vài ngăn old "bẩn" nhất — cân bằng giữa pause time và throughput |
| **Remembered Set (RSet)** | Sổ ghi nhớ: region A tham chiếu region B → RSet của B ghi nhớ A. Dọn B không cần quét toàn heap |
| **SATB (Snapshot-At-The-Beginning)** | Kỹ thuật concurrent marking: ghi lại snapshot object graph lúc bắt đầu, tránh miss object mới tạo trong lúc marking |

**Điểm khác biệt chính:**

| GC | Pause time | Throughput | Heap size phù hợp |
|----|------------|------------|-------------------|
| Parallel GC | Lớn (stop-the-world toàn heap) | Cao | < 4GB |
| CMS | Thấp (concurrent) nhưng fragmentation | Trung bình | < 8GB (deprecated) |
| **G1GC** | **Dự đoán được (target pause time)** | Tốt | **4GB - 32GB+** |
| ZGC/Shenandoah | Rất thấp (< 10ms) | Tốt | > 32GB, low-latency |

---

## 3) Trả lời Middle+

**G1GC chia heap thành nhiều region (1-32MB). Mỗi region mang role: Eden, Survivor, Old, Humongous (> 50% region size).**

- **Young GC:** Chỉ dọn Eden + Survivor regions. Copy object sống sang Survivor/Old. Pause ngắn (~10-50ms).
- **Mixed GC:** Trigger khi old generation occupancy > `InitiatingHeapOccupancyPercent` (mặc định 45%). Dọn young + chọn vài old region có **garbage ratio cao nhất** (Garbage-First) → reclaim memory hiệu quả.
- **Concurrent Marking:** Chạy song song với app thread (SATB). Xác định live object trong old regions.
- **RSet:** Mỗi region có RSet theo dõi incoming reference từ region khác. Giúp young/mixed GC không cần full heap scan.

**Config quan trọng:**
```bash
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200        # Target pause time (default 200ms)
-XX:InitiatingHeapOccupancyPercent=45  # Trigger concurrent marking
-XX:G1HeapRegionSize=16M        # Region size (power of 2, 1-32MB)
```

**Khi dùng G1GC:** Heap 4-32GB, cần pause time predictable, không muốn fragmentation như CMS.

## 4) Trả lời Senior

**Trade-off & Production concerns:**

| Aspect | Chi tiết |
|--------|----------|
| **Humongous allocation** | Object > 50% region size → allocate trực tiếp vào old (humongous region). Quá nhiều humongous → premature old GC, fragmentation. Fix: tăng region size hoặc giảm object lớn. |
| **RSet overhead** | Mỗi reference write → post-write barrier cập nhật RSet. Write-heavy workload (high mutation rate) → RSet bloat, CPU overhead. `-XX:G1RSetUpdatingPauseTimePercent` tune. |
| **Evacuation failure** | Mixed GC không đủ to-space (Survivor/Old free region) để copy object sống → fallback full GC (serial, chậm). Fix: tăng `-XX:G1ReservePercent` (default 10%), giảm pause target. |
| **Concurrent marking cycle** | Nếu allocation rate > marking speed → concurrent marking kịp finish trước khi old full → full GC. Tune: `InitiatingHeapOccupancyPercent` thấp hơn, hoặc tăng marking threads (`-XX:ConcGCThreads`). |
| **String Deduplication** | `-XX:+G1EnableStringDeduplication` — deduplicate char[] nội bộ String. Hiệu quả khi nhiều String trùng lặp (log, JSON). Overhead: CPU scan string table. |
| **Large page / Transparent Huge Pages** | G1GC hoạt động kém trên THP (page fault khi region span huge page). Tắt THP: `echo never > /sys/kernel/mm/transparent_hugepage/enabled`. |
| **Observability** | Dùng `jstat -gc <pid>`, `jcmd <pid> GC.heap_info`, GC log (`-Xlog:gc*:file=gc.log:time,tags`). Theo dõi: pause time p99, mixed GC frequency, evacuation failure count. |

**So sánh G1GC vs ZGC (Java 11+):**
- ZGC: pause < 1ms (colored pointers, load barriers), heap multi-TB. Overhead: ~10-15% throughput loss vs G1GC.
- Chọn ZGC khi: latency critical (trading, gaming), heap > 32GB, JDK 17+ (production ready).
- G1GC vẫn default tốt cho đa số enterprise app Java 17/21.

## 5) 30 giây tóm tắt miệng

> "G1GC chia heap thành region nhỏ, dọn rác theo kiểu **Garbage-First** — ưu tiên region bẩn nhất. Young GC dọn Eden/Survivor nhanh; Mixed GC dọn young + vài old region bẩn nhất. Concurrent marking dùng SATB để tránh miss object. Target pause time configurable (default 200ms). Phù hợp heap 4-32GB, cần pause predictable. Watch out: humongous allocation, evacuation failure, RSet overhead. Java 17+ có ZGC nếu cần sub-ms latency."

## 6) Follow-up / Pitfall

| Pitfall | Nguyên nhân | Giải pháp |
|---------|-------------|-----------|
| **Full GC đột ngột** | Evacuation failure / concurrent marking không kịp | Tăng heap, giảm pause target, tune `G1ReservePercent`, `InitiatingHeapOccupancyPercent` |
| **CPU cao do GC** | RSet overhead / quá nhiều region / marking threads nhiều | Giảm region size, tune `ConcGCThreads`, bật String Deduplication nếu nhiều String trùng |
| **Humongous region đầy** | Nhiều object lớn (byte[], large JSON) | Tăng region size (16-32MB), streaming parse thay vì load toàn bộ |
| **Promotion storm** | Survivor space nhỏ, object trẻ promoted sớm | Tăng `-XX:G1NewSizePercent` / `-XX:G1MaxNewSizePercent` |
